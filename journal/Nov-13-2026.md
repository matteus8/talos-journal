# Prep Configs, Pipelines & Local Staging
While I could generate the configs in this repo and then use talosctl to package them via command line arguments and bundle the image, I want to try and be mature here and use github pipelines...

## The Pipeline Setup
I have added all the typical DevOps work to the repo...
Here is the setup build:
1. The Secret Sauce (`.sops.yaml` and `Age`):
   - Generated a fresh `age` key pair on my Mac.
   - The public key (`age18n9g...`) lives safely in `.sops.yaml` at the root.
   - The private key is saved locally (included in `.gitignore`) and is also added as GitHub Secret (`SOPS_AGE_KEY`).
   - To make sure others can actually see what is being built without exposing private keys, I configured `.sops.yaml` with:
     - `encrypted_regex: '^(token|crt|cert|key|privateKey|secret|clusterSecret|clusterID|ca|acceptedCAs|aescbcEncryptionSecret)$'`
     - This encrypts *only* the cryptographic secrets. All the architecture—static blocks—remains human-readable.
2. The Encrypted Machine Configs (`configs/`):
   - Generated cluster configs for our `thor-edge-lab` cluster.
   - Patched Pi 5 (control plane) to `192.168.1.100` and target disk `/dev/mmcblk0`.
   - Patched Surface 3 (worker) to `192.168.1.106`, target disk `/dev/mmcblk0`, and enabled *TPM 2.0 LUKS disk encryption*
   - Encrypted everything with SOPS: `controlplane.enc.yaml`, `worker.enc.yaml`, and `talosconfig.enc`
3. The GitHub Actions Pipeline (`.github/workflows/talos-pipeline.yaml`):
   - Job 1 (Security Gate & Validation): Scans the repo to ensure no unencrypted keys/configs leaked, installs `sops` and `talosctl`, decrypts in-memory using `secrets.SOPS_AGE_KEY`, and runs `talosctl validate --mode metal`.
   - Job 2 (Edge Image Bundler): Pulls the official base installer images (Surface 3 x86 `metal-amd64` and the `Pi 5 SBC` image) and uploads them as downloadable GitHub [Workflow-Artifacts OR private OCI Registry] so we can grab and flash them quickly.
     > This is slightly geared towards a future optimization but really job 2 right now is overkill.

Because we are doing *Option 2 (Pre-baked / Edge)*, I will generate the cluster secrets and configs on the Mac first, bake them into the installation media, and let the hardware boot straight into the cluster without DHCP or Maintenance Mode.

### Flashing Media: Going Full CLI with `dd`
- For the Surface 3, its going to be bare-metal install
- We boot the Talos installer from the USB stick, targeting the internal eMMC drive (`/dev/mmcblk0` - not `/dev/sda`)
- Once installed, it boots purely from disk like a dedicated server blade.
- While I can use tools like `Raspberry Pi Imager` or `Rufus` for convenienance, for real systems engineering, and the street cred, I'll stick to the classic Unix way: raw command-line `dd` on the Mac terminal. 
  > Writing raw disk blocks with `sudo dd of=/dev/rdisk... bs=4M status=progress` teaches me something new.
  ```bash
  ./scripts/bake-and-flash.sh surface3
  ```

### How Things Look Under the Hood
Without leaking our private cluster keys to third-party build servers (github/gitlab):
1. Image Factory Schematics: We use Talos Image Factory to compile the boot image with this kernel command-line argument:
   ```text
   talos.config=metal-iso
   ```
   This instructs the Talos Linux kernel on boot to scan local drives for a filesystem labeled `metal-iso` and then read `/config.yaml`
2. Local Pre-Baking on the Media:
   Our local Mac script decrypts `worker.enc.yaml` in-memory using our private `age.key`, and creates a partition labeled `metal-iso` directly on the USB stick containing `config.yaml`.
3. Unattended Installation:
   When the Surface 3 boots from that USB stick:
   - It reads `config.yaml` locally off the USB.
   - It sees `dhcp: false` and sets static IP `192.168.1.106`.
   - It reads `UnattendedInstallConfig`, targets the internal eMMC (`/dev/mmcblk0`), sets up *TPM 2.0 LUKS disk encryption*, writes the OS directly to internal storage, and shuts down / reboots.
     - *It skips Maintenance Mode*
     - *No DHCP*
     - *No network push with an `--insecure` flag*

### The Hardware Spec Crash-Out & Role Swap
1. After dusting off this old tablet (which I thought was a Surface Pro 2 or Pro 3) - it turns out, it was just a non-pro **Surface 3**, and looking at the specs... with [2gb of RAM](https://docs.siderolabs.com/talos/v1.14/getting-started/system-requirements).... AAAAAGGHHHHH.... after a short crash out, I composed myself.
    - See [Surface 3 Specs](./Nov-13-2026/surface-3-specs.jpg)
2. Here is why that spec's really frustrated me:
- The RAM (2.00 GB): Sidero's docs say 2GB is the bare minimum for Talos, but that is thin for a control plane. With `etcd` taking ~500MB and `kube-apiserver` taking ~700MB+, my 2GB master node might hit OOO and destroy the Kubernetes API.
- The Disk (eMMC vs SSD): Surface 3 does not have an mSATA or NVMe SSD. It has soldered eMMC flash memory, which registers in Linux as `/dev/mmcblk0` (not `/dev/sda`). If I had blindly set `machine.install.disk: /dev/sda` in my Talos config, it would have tried to wipe my bootable USB stick instead of the internal drive.
- The CPU: The *Intel Atom x7-Z8700* is a *2015 Cherry Trail quad-core* running at *1.6GHz*. My Raspberry Pi 5 runs a modern *Broadcom BCM2712 quad-core Cortex-A76* at *2.4GHz* with **4.0 GiB of RAM and hardware crypto** (`aes`, `sha1`, `sha2`). The Pi 5 runs circles around this little tablet.
- Secure Boot is ON: Just noting the UEFI settings show Secure Boot is active. Before Talos can boot from USB, I have to turn Secure Boot off in UEFI.
- The TPM 2.0 Silver Lining: Looking closely at the specs under `PCR7 Configuration`, the Surface 3 actually has an onboard *TPM 2.0* chip (Intel PTT)! While the Pi 5 doesn't have an onboard TPM out-of-the-box, having TPM 2.0 on the Surface 3 means we can actually demo true hardware-sealed LUKS disk encryption on our worker node to mimic the THOR edge security architecture.

3. The Pivot: Swapping Control Plane & Worker
- After pulling the Pi 5 specs (`hostnamectl`, `free -h`, `cat /proc/cpuinfo`), it confirmed my Pi 5 has **4.0 GiB of RAM** and quad Cortex-A76 cores with hardware crypto acceleration. 
- Because of this, swapping the roles is a no-brainer:
  - **Control Plane $\rightarrow$ Raspberry Pi 5 (`192.168.1.100`):** 4GB of RAM gives `etcd` and `kube-apiserver` the breathing room they need (avoiding the 2GB OOM trap), and the hardware crypto engine handles Talos's continuous mTLS handshakes in silicon without slowing down.
  - **Worker Node $\rightarrow$ Surface 3 (`192.168.1.106`):** 2GB of RAM and an Atom CPU are plenty for a lightweight edge worker running simple consumer pods or sensor simulators. And we target `/dev/mmcblk0` for the internal eMMC install.

### The Hotspot Dilemma
At first I had this clever thought: what if I just connect the Surface 3, the Pi 5, and my Mac to my phone's hotspot? In theory, it creates a completely segregated network away from the rest of my home Wi-Fi traffic.

But - it's not great cause:
1. The Dilemma: My hotspot has "AP Client Isolation" enabled by default, which is actually great for everyday security. Essentially, connected devices can only talk out to the internet, but can't talk to each other. In this setup, the Surface 3 worker has to talk directly to the Pi 5 control plane on port 6443, and my Mac has to reach both on port 50000. On my phone hotspot, this peer-to-peer traffic will likely get dropped. 
2. My hotspot will hand out random DHCP addresses rather than getting the needed static IPs.

### The "No Wi-Fi" Struggle & Cable Dilemma
The main issue I noticed before plugging in a USB stick to the Mac was, *assuming the flash goes well, how does the Surface 3 get network connectivity...?* 
> and yes, ultimitaly, it meant buying yet another cable... but alas it worked... so...
The answer: *It won't without a ethernet cable*
- No GUI, No Shell, No Wifi: As already noted many times, Talos is immutable... so no way to pick a Wi-Fi SSID
- Hardware Limitations: The Surface 3 uses a `Marvell AVASTAR 88W8897` wireless chip. Talos's stripped-down kernel does not ship closed-source proprietary Marvell firmware. (freakin' microsoft)
- While `dd` was writing blocks - I bought the cable (a usb-a cable adapter).
- Tactical Reality: I know in most Defense tactical setups, like Leonardo DRS THOR, its rare to run over consumer Wi-Fi anyway. Also Talos expects a wired Ethernet cable so it can grab its repective IP in the config and begin to bootstrap itself and open port `50000`.

### The Pipeline vs. Local Staging Debate
> THIS IS A WORK IN PROGRESS - OPTIONAL AND LATER WORK BUT STAGED THE COMMIT FOR FUTURE MORE MATURE BUILDS
While setting up the CI pipeline, I thought through some security and architecture questions:
> *If this is a public repository, what happens if we pre-bake the machine configs into the images inside GitHub Actions?*

If the pipeline decrypts the configs and bakes them into a `.raw` or `.iso` image and uploads it as a workflow artifact or container release, anyone on the internet could download and extract the cluster's private mTLS certificates, tokens, and encryption keys. 
Even pushing images to a private registry, like AWS ECR, adds cloud complexity that goes against our bare-metal, air-gapped edge goal. I think we could do that and weigh some tradeoffs, but to keep things simple...

The pipeline is actually just good for:
1. CI as a Declarative Validator: GitHub Actions acts as a security gate. It runs `talosctl validate --mode metal` to ensure our YAML syntax, disk selectors, and network interfaces are 100% compliant, and fails if anyone tries to commit a raw, unencrypted secret.
2. Local Staging Script (`scripts/bake-and-flash.sh`): The actual image retrieval, decryption, and disk writing happens locally on the Mac with the bash script. It auto-detects USB/SD media, and writes to device via `dd`.

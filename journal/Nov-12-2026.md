## Base Line Goal: Tactical Edge & Emulating Rugged Hardware (Leonardo DRS THOR)
I want to model this architecture after real-world tactical edge systems, such as the Leonardo DRS THOR (Tactical, High-Performance Embedded Computing, Open Architecture, Rugged) chassis, which recently won "Best New Product/Service" at AUSA. The THOR chassis is designed to bring compute, high-throughput sensor ingest, and AI to the edge (like combat vehicles). By deploying Talos on my bare-metal lab (laptop control plane and Raspberry Pi 5 worker), I can best simulate this kinda edge node architecture.

## Core concepts
To keep our thinking concise. Here are a few things:
- By default - when you flash Talos onto an SD-card/NVMe/USB for the hardware, and power the hardware on for the first time, it boots into `Maintenance Mode`.
  - In Maintenance Mode:
    - Talos runs basic kernel networking (DHCP) and starts its gRPC API daemon (apid) on port 50000
    - Talos doesn't have the cluster's CA yet, instead, it generates an ephemeral, *self-signed* TLS certificate
  - Two main ways to handle the configuration of the idle hardware that is in maintenance mode:
    - 1. **The quick lab**: Network Pushing the config with `--insecure` flag
      - It looks like this - `talosctl apply-config --insecure --nodes <internal IP addy> --file worker.yaml`
        - The `--insecure` does not mean plain-text HTTP, the connection is still encrypted with TLS because the self-signed cert. The word insecure is like "I am connecting to a device whose TLS cert is self-signed, so I can't cryptographically verify that this IP really belongs to this hardware" (...think, first time SSH, and it asks 'Are you sure you want to trust this host key?')
        - Once the hardware absorbs that YAML file:
          - It writes the config to disk (/system/state/config.yaml)
          - It shuts down Maintenance Mode and reboots apid and uses the real cluster CA
          - From that moment on, `--insecure` is permanently *disabled*. Future commands must present an mTLS client cert signed by the cluster's Talos CA.
    - 2. **The Enterprise**: This is what we are trying to mock up, because securing the edge, like the Leonardo DRS THOR chassis, is the hard part. We can't broadcast configs across an untrusted local switch.
      - Use the Talos Imager (`talosctl image` or `ghcr` or [image factory](https://factory.talos.dev/)):
        - Pre-bake the worker.yaml (configs) into the boot media (SD-card, NVMe, USB) before it reaches hardware
        - When the hardware powers on, the kernel reads the configs directly from local storage
        - The node skips "Maintenance Mode" and joins the cluster with mTLS already established
      - GHCR Releases vs. Talos [Image Factory](https://factory.talos.dev):
        - Why both exist: GHCR (`ghcr.io/siderolabs/...`) hosts vanilla, generic container and installer images. But because Talos has zero package managers (no apt/yum/dnf) and an *immutable rootfs*, you cannot install hardware drivers or firmware at runtime.
        - Image Factory solution: Image Factory compiles custom kernel/initramfs images on demand using a "Schematic". If your edge hardware needs specific extensions (like Raspberry Pi boot firmware overlays, non-free Wi-Fi, or NVIDIA GPU drivers for edge AI inference), Image Factory bakes them directly into the `.raw` or `.iso` image at build time.
        > NOTE: For code examples with SOPS, GitLab CI, and Terraform exploration, see [here](./nov-12-2026/)

## Edge Deployments
As it goes with most bare-metal deployments, an on-prem setup has a few extra hurdles compared to spinning up a Talos cluster on VM's with a cloud provider. At first glance, the two big challenges that came to mind were:

### Challenges (And How They Actually Get Solved)
- Secrets Management: Without a managed secret vault (AWS Secrets Manager/Param-Store - Azure Key Vault) where do sensitive cluster assets (Talos PKI, etcd root CAs, bootstrap tokens) live safely?
- Infra as Code: On bare metal without a hypervisor, can we, or do we even need to use Terraform/OpenTofu to inject certs and configs without cloud `user-data`?

Here were my initial thoughts, followed by a "oh - that makes sense" reality:

### 1. Secrets Management & The PKI Lifecycle
- Initial Thought: When running `talosctl gen config`, it generates root CAs and tokens on a dev laptop. Scripting out a way to push those certs to master and worker nodes ain't right and its not easily scalable. If a node needs this secret bundle to configure itself, how do we protect it in transit and at rest?
- The Solution & How Secrets Actually Flow:
  - Separation of Concerns: Talos actually separates the master secrets bundle (`talosctl gen secrets`) from the node configurations (`controlplane.yaml` and `worker.yaml`). 
  - A worker node does not need the cluster root CA private key or the etcd private key.
  - Where does the encryption/decryption key live?
    - We use `SOPS` (Secrets OPerationS) with `age` for the git repo:
      - The encrypted Talos configs/secret files are committed to remote Git repo
      - The private `age` decryption key lives on the "provisioner" (CI runner, air-gapped bastion, secure laptop)
      - The age decrypt's the config in-memory at deployment time and delivers the unencrypted values to the Talos' node's API (`apid` on port 50000) over mutual TLS.
    > NOTE: From an advasory perspective - if they steal the repo, its just encrpyed files
  - At-Rest Hardware Encryption: Once the Talos node absorbs its config, Talos seal's the disk and config state using the node's onboard `TPM 2.0 chip` via [LUKS](https://docs.siderolabs.com/talos/v1.14/configure-your-talos-cluster/storage-and-disk-management/disk-encryption#configuration) disk encryption. 
    > NOTE: From an adversary perspective - if they steal the physicall edge device, the secrets and configs cannot be decrypted without the physical platform's integrity checks passing - PCR (Platform Configuration Registers).

    > Hardware Note: LUKS is handled by the Linux kernel, so any storage drive supports it, but TPM 2.0 requires physical hardware. My old laptop likely has it built into the CPU (Intel PTT / AMD fTPM), but the Raspberry Pi 5 doesn't natively have a TPM chip. If no TPM is detected, Talos can still encrypt via a static key from my understanding.

### 2. Infrastructure as Code: Terraform vs. Native talosctl + Codebase
- Initial Thought: Sidero Labs maintains an official `siderolabs/talos` Terraform provider, so at first I assumed we would wrap the whole bare-metal deployment in Terraform just like we do in AWS or Azure.
- The Realization: In cloud environments, Terraform makes sense because it 'creates' the virtual machines, subnets, and disks. But on physical bare metal (like my laptop and Pi5 or a vehicle-mounted THOR chassis), Terraform can't create physical motherboards. Wrapping physical hardware in a `terraform.tfstate` file adds state-management baggage and drift issues on the offline or intermittent edge network.
- The Better Path for the Edge (Codebase and `talosctl`): 
  - Instead of fighting TF state files for physical hardware, we do the GitOps flow with the declarative machine configs (encrypted with SOPS), and use native `talosctl` to drive the cluster:
    - Day-0 Declarative Configs in Git: Version-controlled `controlplane.yaml`, `worker-pi5-unit64.yaml`, and patch files.
    - Day-2 Ops: When we need to update DNS, rotate certs, upgrade Kubernetes, we run native gRPC commands:
      - Full config update: `talosctl apply-config -n <IP> --file worker-pi5-unit64.yaml`
      - Small config patch: `talosctl patch mc -n <IP> --patch @patch.yaml`
      - OS upgrade: `talosctl upgrade -n <IP> --image ghcr.io/siderolabs/installer:v1.14.x`
  - Stateless & Air-Gap Ready: No remote Terraform backend or S3 lock files. The state lives in Git and on the physical node itself.

So we still get the full benefits of GitOps and Infrastructure-as-Code, but using native tooling designed for bare-metal immutability rather than cloud VM abstractions.

## Cloud Deployments
Per usual, a talos linux node deployment in the cloud comes with fewer hurdles than on-prem. We can use a secret's vault (AWS/Azure) to get easy HA and backups for our CA cert's and keys if needed, and we can provision the nodes with AMI/Image's and inject certs via terraform user data. 

I would like to try the cloud deployment later, as I suspect it will have its own challanges but be slightly easier. However, for the purposes of keeping things hard and solving real world problems in defense tech, I will be focusing on the edge/on-prem Talos clusters.

## Side quests (archived thoughts)

### AWS Bare Metal Instances
While I could try to mock this with AWS bare metal instances to get a closer replication of a system like Leonardo DRS' THOR, I want to be resourceful, demo a multi arch deployment, and more importantly save money. This is also why I am dropping docker from Nov 10, as the goal is to get as close to prod edge deployment model as possible.

### The Sidero Labs Terraform Provider
While Sidero maintains a solid Terraform provider (`siderolabs/talos`), I decided against using it for this bare-metal lab. It excels when spinning up Talos on cloud VMs or Proxmox, but wrapping physical hardware in a `terraform.tfstate` file introduces state locking and drift headaches on an intermittent connected edge. A version-controlled repo and native `talosctl` gives me the same declarative GitOps with none of the state baggage.

### PXE Booting vs Flashing Images
At first I was also wondering about PXE booting (network booting). From what I read, PXE is great if you have a massive data center with a bunch of servers, because the machine just grabs the Talos OS over the network cable without needing anyone to plug in an NVMe/SD-card/cable/USB. But I've been told that PXE requires setting up your own DHCP and TFTP boot servers, which sounds like a headache for a home lab (and consumer home routers or Pi 5 boot firmware can be finicky with it). 

For our edge setup, just flashing the image directly onto the drive - kind of like how an FDE or technician stages hardware in a depot - is way simpler and keeps things offline ready.

Because THOR is a modular OpenVPX 3U system, I want to model the idea of pre-flashing an NVMe drive (in my lab, an SD card) and snapping it directly into THOR's module. When the Pi 5 powers on with that pre-baked image, it already has the networking and certs, so it skips maintenance mode and joins the laptop control plane automatically on Day-0. 

And for Day-2 fleet maintenance down the road, we won't re-flash or send FDE to the vehicles, we just use the version-controlled codebase and native `talosctl` commands over the air to push live configs/patches or OS upgrades.

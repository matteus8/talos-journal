# Deployment patterns
After reading through several documentation pages, its best to separate the deployment of TALOS Linux into two categories
- Cloud
- Onprem
> Arguably there can be a hybrid deployment, but more on that later

For the purpose of understanding and to demo, I will use an old laptop (master node) and a Raspberry Pi 5 (worker node) for an on-prem bare-metal deployment of talos linux.
> NOTE: Using a single old laptop for control plane is not idea, but its what I have. In a real-world we run HA 3-node control plane.

## Base Line Goal: Edge & Emulating Rugged Hardware (Leonardo DRS THOR)
I want to model this architecture after real-world edge systems, such as the Leonardo DRS THOR (Tactical, High-Performance Embedded Computing, Open Architecture, Rugged) chassis, which recently won "Best New Product/Service" at AUSA. The THOR chassis is designed to bring compute, high-throughput sensor ingest, and AI to the edge (like combat vehicles). By deploying Talos on a bare-metal lab (laptop control plane and Pi 5 worker), I can best simulate this kinda edge node architecture.

## Core concepts
To keep our thinking concise. Here are a few things:
- By default - when you flash Talos onto an SD-card/NVMe/USB for the hardware, and power the hardware on for the first time, it boots into `Maintenance Mode`.
  - In Maintenance Mode:
    - Talos runs basic kernel networking (DHCP) and starts its gRPC API daemon (apid) on port 50000
      > NOTE: DHCP problem addressed later
    - Talos doesn't have the cluster's CA yet, instead, it generates an ephemeral, *self-signed* TLS certificate
  - Two main ways to handle the configuration of the idle hardware that is in maintenance mode:
    - 1. **quick lab**: Network Pushing the config with `--insecure` flag
      - It looks like this - `talosctl apply-config --insecure --nodes <internal IP addy> --file worker.yaml`
        - The `--insecure` does not mean plain-text HTTP, the connection is still encrypted with TLS because the self-signed cert. The word insecure is like "I am connecting to a device whose TLS cert is self-signed, so I can't cryptographically verify that this IP really belongs to this hardware" (...think, first time SSH, and it asks 'Are you sure you want to trust this host key?')
        - Once the hardware absorbs that YAML file:
          - It writes the config to disk (/system/state/config.yaml)
          - It shuts down Maintenance Mode and reboots apid and uses the real cluster CA
            > NOTE: if configured right it also encrptys the config if hardware supports TPM 2.0
          - From that moment on, `--insecure` is permanently *disabled*. Future commands must present an mTLS client cert signed by the cluster's Talos CA.
    - 2. **The Enterprise**: This is what we are trying to mock up, because securing the edge, like the Leonardo DRS THOR chassis, is the hard part. We can't broadcast configs across an untrusted local switch or have access to DHCP or Time.
      - Use the Talos Images (`talosctl image` or `ghcr` or [image factory](https://factory.talos.dev/)):
        - Pre-bake the worker.yaml (configs) into the boot media (SD-card, NVMe) before it reaches hardware
        - When the hardware powers on, the kernel reads the configs directly from local storage
        - The node skips "Maintenance Mode" and joins the cluster with mTLS already established
      - GHCR Releases vs. Talos [Image Factory](https://factory.talos.dev):
        - Why both exist: GHCR (`ghcr.io/siderolabs/...`) hosts vanilla, generic container and installer images. But because Talos has zero package managers (no apt/yum/dnf) and an *immutable rootfs*, you can't install hardware drivers or firmware at runtime.
        - Image Factory solution: Image Factory helps compile custom kernel images using a "Schematic". If edge hardware needs specific extensions like NVIDIA GPU drivers for edge AI inference, Image Factory bakes them directly into the `.raw` or `.iso` image at build time.
        - What about air-gapped builds: Usually, devs pushing patches have internet access, build the images via Image Factory, and then transfer them over the guard/CDS to edge domain. But if you're in an isolated environment where policy forbids sending proprietary hardware schematics or kernel modules, you can run the local `imager` container (`ghcr.io/siderolabs/imager`) offline against internal mirrors.
        > NOTE: For code examples with SOPS, GitLab CI, and Terraform exploration, see [here](./Nov-12-2026/)

## Edge Deployments
As it goes with most bare-metal deployments, an on-prem edge setup's have a few extra hurdles compared to spinning up a Talos cluster on VM's with a cloud provider. At first glance, the two big challenges that came to mind were:

### Challenges (And How They Actually Get Solved)
- Secrets Management: Without a managed secret vault (AWS Secrets Manager/Param-Store - Azure Key Vault) where do sensitive cluster assets (Talos PKI, etcd root CAs, bootstrap tokens) live safely?
- Infra as Code: On bare metal without a hypervisor, can we, or do we even need to use Terraform/OpenTofu to inject certs and configs without cloud `user-data`?

Here were my initial thoughts, followed by a "oh - that makes sense" reality:

### 1. Secrets Management & The PKI Lifecycle
- Initial Thought: When running `talosctl gen config`, it generates root CAs and tokens on a dev laptop. Scripting out a way to push those certs to master and worker nodes ain't right and its not easily scalable or secure. If a node needs this secret bundle to configure itself, how do we get it there.
- The Solution & How Secrets Actually Flow:
  - Separation of Concerns: Talos actually separates the master secrets bundle (`talosctl gen secrets`) from the node configurations (`controlplane.yaml` and `worker.yaml`). 
  - A worker node does not need the cluster root CA private key or the etcd private key 
    > NOTE: The `worker.yaml` still contains the cluster join token and CA certs, so it is still a sensitive file.
  - Where does the encryption/decryption key live?
    - We use `SOPS` (Secrets OPerationS) with `age` for the git repo:
      - The encrypted Talos configs (`worker-pi5.enc.yaml`) and admin client credentials (`talosconfig.enc`) are committed to the remote Git repo.
      - The private `age` decryption key lives on the "provisioner" (CI runner, air-gapped bastion, secure laptop).
      - The age key decrypts the configs in-memory at deployment time and delivers the unencrypted values to the Talos node's API (`apid` on port 50000) over mutual TLS.
    > NOTE: From an adversary perspective - if they steal the repo, its just encrypted files.
  - At-Rest Hardware Encryption: In prod, edge hardware (like a fielded THOR chassis), Talos seals the disk and config state using the node's onboard `TPM 2.0 chip` via [LUKS](https://docs.siderolabs.com/talos/v1.14/configure-your-talos-cluster/storage-and-disk-management/disk-encryption#configuration) disk encryption and PCR (Platform Configuration Registers) measured boot.
    > NOTE: From an adversary perspective - if they physically capture the vehicle or pull the drive, the secrets and configs cannot be decrypted without the physical platform passing hardware integrity checks.

    > In our Lab (Pi 5 & TPM): The Pi5 doesnt have a TPM 2.0 chip or native UEFI Secure Boot - so while prod uses it, we will not due to hardware limitations.

### 2. Infrastructure as Code: Terraform vs. Centralized Push with Native talosctl
- Initial Thought: Sidero Labs maintains an official `siderolabs/talos` Terraform provider, so at first I assumed we would wrap the whole bare-metal deployment in Terraform just like we do in AWS or Azure.
- The Realization: In cloud environments, Terraform makes sense because it 'creates' the virtual machines, subnets, and disks. But on physical bare metal (like my laptop and Pi5 or a vehicle-mounted THOR chassis), Terraform can't create physical motherboards. Wrapping physical hardware in a `terraform.tfstate` file adds state-management baggage and drift issues for the edge network.
- The Better Path for the Edge (Centralized Push Deployment via CI): 
  - Instead of fighting TF state files for physical hardware, we keep declarative machine configs in git (encrypted with SOPS), and use centralized push deployment via CI and native `talosctl` to drive the cluster:
    - Day-0 Declarative Configs in Git: Version-controlled `controlplane.yaml`, `worker-pi5.enc.yaml`, `talosconfig.enc`, and patch files.
    - Day-2 Ops: When we need to update DNS, rotate certs, or upgrade Kubernetes, we run native gRPC commands pushed from CI or a secure staging laptop:
      - Full config update: `talosctl apply-config -n <IP> --file /tmp/worker-pi5.yaml --talosconfig /tmp/talosconfig`
      - Small config patch: `talosctl patch mc -n <IP> --patch @patch.yaml`
      - OS upgrade: `talosctl upgrade -n <IP> --image ghcr.io/siderolabs/installer:v1.14.x`
  - Stateless & Air-Gap Ready: No remote Terraform backend or S3 lock files. The desired config lives in Git, and the actual state lives on the physical node itself.

So we still get the benefits of declarative Infrastructure-as-Code, but using native tooling designed for bare-metal immutability rather than cloud VM abstractions.

### 3. Tactical Edge Gotchas (Time Sync & DHCP)
Two gritty edge details that often get overlooked:

- DHCP Failures: Most lab env's with Wi-Fi routers, do okay with DHCP - but in isolated enviornments like on THOR chassis, there is rarly a DHCP server running or avaiable. Typically you have to bypass DHCP and provide a static IP kernel arguments for Talos to boot - like `ip=192.168.1.101::192.168.1.1:255.255.255.0:worker-pi5:eth0:off` in `cmdline.txt`.
- Time Sync (NTP / RTC): Everything in Talos and Kubernetes relies on mTLS certs. Typical mTLS failures like `certificate has expired or is not yet valid` occure because the system clock drifts or resets. For DDIL enviornments, because there is no public internet NTP pools, often boxes like THOR handle this with GPS/GNSS time receivers (IEEE 1588 PTP), or a hardware RTC chip with a dedicated battery.
  - Real world - THOR chassis: THOR itself doesn't generate GPS time — it’s a 3U VPX, SOSA-aligned (Sensor Open
      Systems Architecture) rugged chassis with open payload slots.
      - In a real vehicle setup, one of those slots hosts a dedicated military or commercial-grade GNSS/GPS receiver card. That card pulls atomic time from satellites (continuous, leap-second-free) and acts as an on-chassis time server, distributing time across THOR's backplane via IEEE 1588 PTP (Precision Time Protocol) to all the compute blades running Talos.
  > Lab Pi5 NOTE: The Pi5 doesn't have an RTC battery by default. If my Pi5 reboots while disconnected from home Wi-Fi (no internet NTP), its clock resets and blows up Talos/Kubernetes mTLS handshakes, until time is manually restored.

## Cloud Deployments
Per usual, a talos linux node deployment in the cloud comes with fewer hurdles than on-prem. We can use a secret's vault (AWS/Azure) to get easy HA and backups for our CA cert's and keys if needed, and we can provision the nodes with AMI/Image's and inject certs via terraform user data. 

I would like to try the cloud deployment later, as I suspect it will have its own challenges but be slightly easier. However, for the purposes of keeping things hard and solving real world problems in defense tech, I will be focusing on the edge/on-prem Talos clusters.

## Side quests (archived thoughts)

### AWS Bare Metal Instances
While I could try to mock this with AWS bare metal instances to get a closer replication of a system like Leonardo DRS' THOR, I want to be resourceful, demo a multi arch deployment, and more importantly save money. This is also why I am dropping docker from Nov 10, as the goal is to get as close to prod edge deployment model as possible.

### The Sidero Labs Terraform Provider
While Sidero maintains a solid Terraform provider (`siderolabs/talos`), I decided against using it for this bare-metal lab. It excels when spinning up Talos on cloud VMs or Proxmox, but wrapping physical hardware in a `terraform.tfstate` file introduces state locking and drift headaches on an intermittent connected edge. A version-controlled repo and native `talosctl` centralized push gives me similar declarative automation without tf state baggage.

### PXE Booting vs Flashing Images
At first I was also wondering about PXE booting (network booting). From what I read, PXE is great if you have a massive data center with a bunch of servers, because the machine just grabs the Talos OS over the network cable without needing anyone to plug in an NVMe/SD-card/cable/USB. But I've been told that PXE requires setting up your own DHCP and TFTP boot servers, which sounds like a headache for a home lab (and consumer home routers or Pi 5 boot firmware can be finicky with it). 

For our edge setup, just flashing the image directly onto the drive - kind of like how an FDE or technician stages hardware in a depot - is way simpler and keeps things offline ready.

Because THOR is a modular OpenVPX 3U system, I want to model the idea of pre-flashing an NVMe drive (in my lab, an SD card) and snapping it directly into THOR's module. When the Pi 5 powers on with that pre-baked image, it already has the networking and certs, so it skips maintenance mode and joins the laptop control plane automatically on Day-0. 

And for Day-2 fleet maintenance down the road, we won't re-flash or send Forward Deploy Eng. to the vehicles, we just use the version-controlled codebase and native `talosctl` commands pushed over the air to deploy live configs/patches or OS upgrades.

### Crossplane
Just like why we drop Terraform for complexity, while I love using [Crossplane](https://www.crossplane.io/) instead of Terraform... This is mainly built for large cloud deployments and is out of scope for this type of deployment. For bare-metal bootstrapping its unnecessary complexity compared to Talos' native CLI.

# Deployment patterns
After reading through several documentation pages, its best to seperate the deployment of TALOS Linux into two catagories
- Cloud
- Onprem
> Arguably there can be a hybrid deployment, but more on that later

For the purpose of understanding and to demo, I will use an old laptop (master) and a Raspberry Pi 5 (worker) for an on-prem bare-metal deployment.

## Core concepts
To keep our thinking concise. Here are a few things:
- By default - when you flash Talos onto an SD-card/NVMe/USB for the hardware, and power the hardware on for the first time, it boots into `Maintenance Mode`.
  - In Maintenance Mode:
    - Talos runs basic kernel networking (DHCP) and starts its gRPC API daemon (apid) on port 50000
    - Talos doesn't have the cluster's CA yet, instead, it generates an ephemeral, *self-signed* TLS certificate
  - Two main ways to handle this and configure idle hardware that is in maintenance mode:
    - 1. **The quick lab**: Network Pushing the config with `--insecure` flag
      - It looks like this - `talosctl apply-config --insecure --nodes <internal IP addy> --file worker.yaml`
        - The `--insecure` does not mean plain-text HTTP, the connection is still encrypted with TLS because the self-signed cert. The word insecure is like "I am connecting to a device whose TLS cert is self-signed, so I can't cryptographically verify that this IP really belongs to this hardware" (...think, first time SSH, and it asks 'Are you sure you want to trust this host key?')
        - Once the hardware absorbs that YAML file:
          - It writes the config to disk (/system/state/config.yaml)
          - It shuts down Maintenance Mode
          - It reboots apid and uses the real cluster CA
          - From that moment on, `--insecure` is permanently *disabled*. Future commands must present an mTLS client cert signed by the cluster's Talos CA.
    - **The Enterprise**: 
    > This is what we are trying to mock up, because securing the edge, like the Leonardo DRS THOR chassis, is the hard part. We can't broadcast configs across an untrusted local switch.
      - Use the Talos Imager (`talosctl image` or `siderolabs/imager` or [image factory](https://factory.talos.dev/)):
        - Pre-bake the worker.yaml (configs) into the boot media (SD card, NVMe drive, USB) before it reaches hardware
        - When the hardware powers on, the kernel reads the configs directly from local storage
        - The node skips "Maintenance Mode" and joins the cluster with mTLS already established
        > NOTE: For a more mature deployment model we are using, SOPS and Talos' Terraform module [here](./nov-12-2026/)

## On-Prem & Bare-Metal Challenges (And How They Actually Get Solved)
As it goes with most bare-metal deployments, an on-prem setup has a few extra hurdles compared to spinning up a Talos cluster on VM's with a cloud provider. At first glance, the two big challenges that came to mind were:
- Secrets Management: Without a managed secret vault (AWS Secrets Manager/Param-Store - Azure Key Vault) where do sensitive cluster assets (Talos PKI, etcd root CAs, bootstrap tokens) live safely?
- Infra as Code: On bare metal without a hypervisor, can we still use Terraform/OpenTofu to inject certs and configs without cloud `user-data`?

Here were my initial thoughts, followed by a "oh - that makes sense" reality:

## 1. Secrets Management & The PKI Lifecycle
- Initial Thought: When running `talosctl gen config`, it generates root CAs and tokens on a dev laptop. Scripting out a way to push those certs to master and worker nodes ain't right and its not easily scalable. If a node needs this secret bundle to configure itself, how do we protect it in transit and at rest?
- The Solution & How Secrets Actually Flow:
  - Separation of Concerns: Talos actually separates the master secrets bundle (`talosctl gen secrets` or `talos_machine_secrets` in Terraform) from the node configurations (`controlplane.yaml` and `worker.yaml`). 
  - A worker node does not need the cluster root CA private key or the etcd private key.
  - Where does the encryption/decryption key live?
    - If we use `SOPS` (Secrets OPerationS) with `age`: The encrypted machine configs/secrets are committed to Git. The private `age` decryption key lives on the "provisioner" (the CI/CD runner, air-gapped bastion, secured laptop). 
    - The Talos node itself never gets the SOPS key (if hardware gets stolen adversary would get it). The "provisioner" uses the SOPS key to decrypt the config in-memory at deployment time and delivers the unencrypted values to the Talos' node's API (`apid` on port 50000) over mutual TLS.
  - At-Rest Hardware Encryption: Once the Talos node absorbs its config, Talos can seal the disk and state using the node's onboard `TPM 2.0 chip` via [LUKS](https://docs.siderolabs.com/talos/v1.14/configure-your-talos-cluster/storage-and-disk-management/disk-encryption#configuration) disk encryption. Even if an adversary physically steals the edge chassis, the secrets and configs cannot be decrypted without the physical platform's integrity checks passing - PCR (Platform Configuration Registers).
    > Hardware Note: LUKS is handled by the Linux kernel, so any storage drive supports it, but TPM 2.0 requires physical hardware. My old laptop likely has it built into the CPU (Intel PTT / AMD fTPM), but the Raspberry Pi 5 doesn't nativly had TPM chip. If no TPM is detected, Talos can still encrypt via a static key from my understanding.

## 2. Infrastructure as Code: The Sidero Labs Terraform Provider
- Initial Thought: I assumed that because we are on bare metal without cloud APIs or a popular hypervisor, Terraform wouldn't be able to inject user-data or automate the node bootstrapping.
- Solution: I was pleasantly surprised to learn that Sidero Labs maintains an official `siderolabs/talos` Terraform Provider. In prod, and what we will do later, is, instead of manually running CLI commands and copying YAML files, we will let Terraform handle the full lifecycle:
  - `resource "talos_machine_secrets"`: Generates and manages the entire cluster PKI bundle inside Terraform state (which can be backed by an encrypted backend (like SOPS) or HashiCorp Vault).
  - `data "talos_machine_configuration"`: Renders the declarative machine configs for both control plane and worker nodes with kernel arguments, static network configs, and extensions.
  - `resource "talos_machine_configuration_apply"`: Injects the config into bare-metal node's IP over Talos API port 50000 — which is similar to the cloud `user-data`.
  - `resource "talos_machine_bootstrap"`: Triggers the etcd bootstrap on the first control plane node once the config is applied.
  - `resource "talos_cluster_kubeconfig"`: Retrieves the admin `kubeconfig` once the cluster reaches consensus.

So we get the full GitOps and IaC automation on bare metal, just like in the cloud.

## Cloud Deployments
Per usual, a talos linux node deployment in the cloud comes with fewer hurdles than on-prem. We can use a secret's vault (AWS/Azure) to get easy HA and backups for our CA cert and keys, and we can provision the nodes with  AMI/Image's and inject certs via terraform user data.
